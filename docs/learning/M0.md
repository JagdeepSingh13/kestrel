## Step 1: uv

### What
Installed `uv` (0.13.7, via Homebrew) and used it to install Python 3.12.16.

### Why
A Python project needs four things:

| Job | Old tool | uv command |
|---|---|---|
| Install a Python version | pyenv | `uv python install 3.12` |
| Isolated env per project | venv / virtualenv | `uv venv` (automatic) |
| Install dependencies | pip | `uv add`, `uv sync` |
| Pin exact versions for everyone | pip-tools / poetry lock | `uv.lock` (automatic) |

Before uv you combined 3 to 4 tools. uv does all of them, written in Rust, 10 to 100x faster than pip.

### Concept
- **Interpreter:** the `python` program itself. This Mac had three: `/usr/bin/python3` (3.9, Apple's, do not touch), Homebrew 3.14, and now uv's 3.12 in `~/.local/share/uv/python/`. Kestrel needs 3.12+ for newer syntax like `type X = ...` and better typing.
- **Virtual environment (`.venv/`):** a folder with a link to an interpreter plus its own `site-packages`. Each project's dependencies stay separate, so two projects can need different `httpx` versions.
- **Lockfile (`uv.lock`):** `pyproject.toml` says "httpx >= 0.27". The lockfile records the exact version and hash that was installed, including dependencies of dependencies. Commit it, so CI and every machine get the identical set.
- **`uv run <cmd>`:** syncs `.venv` with the lockfile, then runs the command inside it. No `source .venv/bin/activate` needed. This is why the PATH warning from the install does not matter for us.

### Try it
```bash
uv --version
uv python list --only-installed
uv run --no-project --python 3.12 python -c "import sys; print(sys.version, sys.executable)"
```
The last one runs a throwaway 3.12 interpreter (`--no-project` = ignore any pyproject in this folder). Note `sys.executable` points into uv's folder, not `/usr/bin`.

### Check yourself
1. What is the difference between `pyproject.toml` dependencies and `uv.lock`?
2. Why not just `pip install` everything into the system Python?
3. What does `uv run pytest` do before it runs pytest?

<details><summary>Answers</summary>

1. pyproject lists allowed ranges you chose; the lockfile pins exact resolved versions (with hashes) of everything, including transitive deps.
2. Global installs collide between projects, can break OS tools that depend on system Python, and are not reproducible on another machine.
3. Checks `.venv` exists and matches `uv.lock` (creating or syncing it if not), then runs pytest from inside that env.
</details>

## Step 2a: git + GitHub remote

### What
`git init -b main`, added remote `origin` = `git@github.com:JagdeepSingh13/kestrel.git`, staged files. `private/` is excluded by `.gitignore`.

### Concept
- **Repository:** `.git/` folder holding every committed version of the project.
- **Three areas:** working tree (files on disk), staging area (`git add` picks what goes in the next commit), commits (permanent snapshots).
- **Remote:** a named URL of another copy of the repo. `origin` is the convention for "main copy on GitHub". `git push` sends commits there.
- **SSH URL (`git@github.com:...`):** authenticates with your SSH key instead of a password.
- **`.gitignore`:** paths git never tracks. Check a path with `git check-ignore -v <path>`.
- **Conventional commits:** `type: summary`, e.g. `docs: add spec v0.2`. Types: `feat`, `fix`, `test`, `docs`, `refactor`, `chore`, `ci`. Makes history scannable and enables auto changelogs.

### Try it
```bash
git status
git remote -v
git check-ignore -v private/kestrel-project-handoff.pdf
```

### Check yourself
1. What is the difference between `git add` and `git commit`?
2. The GitHub repo is public. How do we make sure the handoff PDF never reaches it?

<details><summary>Answers</summary>

1. `add` stages changes for the next snapshot; `commit` records the staged snapshot permanently in history.
2. `private/` is in `.gitignore`, so `git add -A` skips it. Verify with `git check-ignore` or `git status` before committing.
</details>

## Step 2b: package layout + `kestrel --version`

### What
Created the installable package and its first command.

```
pyproject.toml          # project metadata, deps, build backend, entry point
.python-version         # "3.12": which interpreter uv uses here
uv.lock                 # exact resolved versions (generated, committed)
src/kestrel/
  __init__.py           # makes `kestrel` a package, re-exports __version__
  __about__.py          # version + name, single source of truth
  __main__.py           # enables `python -m kestrel`
  cli/__init__.py
  cli/app.py            # Typer app with --version / -V
```

Runtime deps: `typer`, `rich`. Dev group: `pytest`, `pytest-asyncio`, `ruff`, `pyright`. `.gitignore` now also covers caches, `.venv/`, build output, `.env`, editor and OS files.

### Why
- **`src/` layout:** the package is not importable from the repo root by accident. Tests and `uv run` always use the *installed* package, so a missing file in the build shows up locally, not after publishing.
- **One version source:** the version lives only in `__about__.py`. Hatchling reads it at build time (`dynamic = ["version"]`), the CLI imports it. No drift between `pyproject.toml` and code.
- **Entry point:** `[project.scripts] kestrel = "kestrel.cli.app:app"` makes the installer generate a `kestrel` executable in `.venv/bin/` that calls `app()`.

### Concept
- **Build backend (hatchling):** the tool that turns the source tree into a wheel. uv is the frontend that asks it to. `[build-system]` names it; `[tool.hatch.*]` configures it.
- **Editable install:** `uv sync` installs the project itself in editable mode. `.venv` points at `src/`, so code edits take effect without reinstalling.
- **Dependency groups (PEP 735):** `[dependency-groups] dev` holds tools for developers only. They are installed by `uv sync` but are not shipped to users who `pip install kestrel`.
- **Typer callback:** `@app.callback()` defines options on the top-level command (before any subcommand). `is_eager=True` makes `--version` run first and exit, even if other args are invalid.
- **`Annotated[bool, typer.Option(...)]`:** the modern Typer style. The type is the real type (`bool`); the metadata rides alongside, so pyright sees a plain bool.
- **`__main__.py`:** Python runs this file for `python -m kestrel`. Useful when the script dir is not on PATH.

### Walkthrough (`cli/app.py`)
1. `typer.Typer(no_args_is_help=True)`: bare `kestrel` prints help instead of doing nothing.
2. `_version_callback` gets the option's value. If true, print `kestrel 0.0.0` and `raise typer.Exit()` (clean exit code 0).
3. `main` is the callback with one option. Its body is empty: subcommands (`doctor`, `ask`, `run`) attach in later milestones.

Two things hit while building:
- `readme = "README.md"` in pyproject made the build fail because README comes in a later step. Removed it for now (also `license`, which goes in with LICENSE). Both come back in those steps.
- `ruff format --check .` flags `docs/SPEC.md`: ruff 0.17 also formats Python code blocks inside Markdown. Step 3 decides whether to exclude `docs/`.

### Try it
```bash
uv run kestrel --version
uv run kestrel -V
uv run python -m kestrel --version
uv run kestrel
ls .venv/bin/kestrel && head -5 .venv/bin/kestrel
uv tree
```
`head` shows the generated launcher script. `uv tree` shows typer pulling in click, rich, shellingham.

### Check yourself
1. Where would you change the version, and how does the CLI and the wheel both pick it up?
2. Why does `src/` layout catch packaging mistakes that a flat layout hides?
3. What would break if `is_eager=True` were removed?

<details><summary>Answers</summary>

1. Only `src/kestrel/__about__.py`. Hatchling reads `__version__` from that path at build time; `cli/app.py` imports it at runtime.
2. With a flat layout, Python imports the package from the current directory, so tests pass even if the package is not installed or a file is missing from the build. With `src/`, the only way to import `kestrel` is the installed copy.
3. Typer would process `--version` in normal order, so a future required option or a bad subcommand could error before the version prints. Eager options run first.
</details>
